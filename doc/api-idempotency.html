What the word actually means

An operation is idempotent if performing it N ≥ 1 times leaves the server in the same state as performing it once. Formally, f(f(x)) = f(x).

The part people get wrong

Idempotency constrains the effect on server state, not the response the client receives. DELETE /orders/42 is idempotent even though the first call returns 204 and the second returns 404. The order is gone either way. Judging idempotency by comparing response bodies will lead you astray.

Four properties people conflate

PropertyMeansProtects against
SafeNo state change at all. Read-only.Crawlers, prefetch, speculative requests
IdempotentRepeating it changes nothing further.Retries by the same client
CacheableThe response may be stored and reused.Latency and origin load
Concurrency-safeInterleaved writes don't corrupt or lose data.Two different clients writing at once

Every safe method is idempotent; the reverse isn't true. And idempotency gives you nothing against lost updates from concurrent writers — that needs ETag / If-Match or a version column. Two separate concerns, routinely mashed together.

Method semantics

MethodSafeIdempotentWhy
GET / HEADyesyesPure read.
OPTIONS / TRACEyesyesMetadata only.
PUTnoyesFull replacement at a known URI. Writing the same document twice lands on the same state.
DELETEnoyesTarget ends up absent regardless of how many times you ask.
POSTnonoThe server picks the URI, so each call is a new resource. This is where the money bugs live.
PATCHnodependsNot guaranteed by spec. {"balance": 500} is idempotent; {"op":"increment","by":1} is not.
Semantics are a promise, not a mechanism

HTTP declaring PUT idempotent doesn't make your PUT handler idempotent. If it appends to an audit table, fires a webhook, or increments a counter, you've broken the contract — and intermediaries that legitimately retry idempotent methods will duplicate those effects for you, silently.

Why retries are unavoidable

When a request times out, exactly three things could have happened: it never arrived; it arrived, succeeded, and the response was lost; or it arrived and failed. The client cannot distinguish these. This is the Two Generals problem, and it has no solution — you cannot achieve exactly-once delivery over an unreliable network.

What you can achieve is at-least-once delivery plus idempotent processing, which yields effectively-once semantics. Retries stop being dangerous, so every layer is free to retry: SDKs, service meshes, load balancers, mobile clients on flaky networks, queue consumers after a rebalance.

Idempotency keys

For operations that aren't naturally idempotent — POST /charges, POST /transfers — the client supplies a unique token identifying the logical operation. The server records what it did under that token and replays the answer on any repeat.

# The wire format (IETF httpapi draft; Stripe, Adyen, Square, PayPal all use it)
POST /v1/charges HTTP/1.1
Host: api.example.com
Idempotency-Key: 4f2a91c8-9d3e-4b7a-8f11-2c6e5d0a7b39
Content-Type: application/json

{"amount": 5000, "currency": "usd", "customer": "cus_9182"}

Rules for generating them

  • Generated by the client, once, before the first attempt. Persist it alongside the retry loop. A key regenerated per attempt defeats the entire mechanism — this is the single most common client-side bug.
  • One key per logical intent, not per HTTP call. "Pay invoice #8891" gets one key. Paying it again next month is a different intent and needs a new one.
  • Opaque and collision-free. UUIDv4 is the default. UUIDv7 additionally sorts by time, which helps index locality and expiry sweeps.
  • Never derived from mutable state. A key built from hash(cart_contents) breaks the moment a customer legitimately buys the same thing twice.
  • Scoped server-side by tenant and endpoint. The uniqueness domain is (api_key, endpoint, key). A global namespace lets one tenant's key collide with — or read back — another's response.

Request fingerprinting

Store a hash of the request alongside the key. On a repeat, compare: matching fingerprint means a genuine retry, mismatched means the client reused a key for different content — a bug worth surfacing as 422 Unprocessable Content rather than silently returning the old answer.

fingerprint = sha256(method ‖ path ‖ canonical_json(body))

Canonicalise before hashing (sort keys, normalise numbers) or map reordering will produce false mismatches. Exclude volatile fields — trace IDs, client timestamps, User-Agent — or every retry from a different pod fails validation.

Often you don't need keys at all

Key infrastructure is real cost: a table, a TTL sweeper, an extra round trip, a state machine. Reach for cheaper structural options first.

TechniqueShapeGood for
Client-assigned IDPUT /orders/{uuid}Creation you control the ID for. Retry is an upsert no-op. Free.
Unique business constraintUNIQUE(tenant, invoice_no)The database rejects the duplicate; catch the violation and return the existing row.
Guarded state transitionUPDATE … WHERE status='paid'Retry affects 0 rows and is harmless. Check the row count, don't assume.
Conditional writeIf-Match: "v7" → 412Gives you optimistic concurrency and replay protection at once.
Two-phase intentPOST /intents then POST /intents/{id}/confirmThe confirm step is naturally idempotent against a known resource.
Rule of thumb

Reserve idempotency keys for irreversible side effects you can't express as a constraint: money movement, outbound email and SMS, third-party API calls, physical fulfilment.

Reference implementation



  

    The one invariant
    
The business effect and the saved receipt must commit atomically. Same transaction, same database. Write the charge and then update the key in a second transaction and you've reintroduced the exact ambiguity you set out to eliminate — now with extra tables.

Retention

  
24 hours is the common default (Stripe's). It needs to comfortably exceed your longest client retry window, including a mobile app that retries when the user reopens it tomorrow. Longer TTLs cost storage; shorter ones silently stop protecting anyone.

  
Whatever you choose, document it. After expiry a repeated key is treated as a brand-new request, and callers need to know that boundary exists. Sweep with a batched, indexed delete — DELETE … WHERE expires_at < now() LIMIT 10000 in a loop beats one enormous statement holding locks.


  
What to store in the receipt

  
    
    
  • Status code, response body, and any headers the client depends on (Location, ETag).
    • 
    
  • Large payloads: store the resource ID instead and re-serialise on replay. Cheaper, but it means replays reflect current state — fine for most APIs, wrong if callers rely on byte-identical replays.
    • 
    
  • Mark replays with a response header such as Idempotent-Replayed: true. Costs nothing; invaluable when you're staring at a dashboard trying to explain a traffic pattern.
    • 
  


  

    Don't cache failures indiscriminately
    
Deterministic 4xx (validation) can be saved — replaying it is correct and cheap. Transient 5xx and timeouts must release the key so a retry can actually re-execute. Persist a 500 as a completed receipt and you've permanently poisoned that operation: every retry replays the failure forever.

  


  
Propagating downstream

  
If your handler calls Stripe, your own idempotency is worthless unless that call is protected too. Derive the downstream key deterministically from yours so a retry produces the same token:


downstream_key = sha256(our_key ‖ ":stripe:charge")

// A fresh uuid.New() here would double-charge on retry.
// The derivation must be pure — no clocks, no randomness.







  
Races and recovery


  
Never check-then-act

  
SELECT followed by INSERT is a time-of-check-to-time-of-use race. Two concurrent retries both read "not found", both proceed, both charge. Claim the key in a single atomic statement and let the unique constraint arbitrate.


-- Postgres
INSERT INTO idempotency_keys (...) VALUES (...)
ON CONFLICT (tenant_id, endpoint, key) DO NOTHING
RETURNING id;          -- zero rows means someone else owns it

-- Redis
SET idem:{tenant}:{ep}:{key} "in_progress" NX PX 30000


  
Losing the race

  
The loser has two reasonable options:

  
    
    
  • Return 409 Conflict with a Retry-After hint. Simple, holds no resources, pushes the wait to the client. Stripe's idempotency_key_in_use.
    • 
    
  • Block and poll until the winner completes, then replay its response. Nicer for callers, but it pins a connection and needs its own timeout — otherwise a slow winner turns into a thread-pool outage.
    • 
  


  
The stuck in-progress problem

  
A pod claims a key, then gets OOM-killed. The row sits in_progress forever and every retry gets 409 — the operation is permanently wedged. Fix it with a lease: store lease_expires_at, and let a later request take over an expired claim.

  

    Leases don't fence zombies
    
An expired lease means "probably dead", not "definitely dead". The original process may be alive behind a network partition and about to commit. Two defences: keep the lease longer than your hard request timeout, and put a real uniqueness constraint on the underlying resource so a takeover physically cannot produce a second charge. Idempotency keys are a fast path; the database constraint is the backstop.

Idempotency is not concurrency control

  
Two different users editing the same document with different keys will both succeed, and the second overwrites the first. Nothing about idempotency prevents that. Add versioning:


GET  /docs/7        → 200  ETag: "v41"
PUT  /docs/7        If-Match: "v41"   → 200 OK
PUT  /docs/7        If-Match: "v41"   → 412 Precondition Failed
                                        (someone advanced it to v42)







  
Beyond HTTP: queues and streams

  
The same problem, different transport. A consumer processes a message, then dies before committing its offset. On rebalance, another consumer replays it. At-least-once delivery is the norm, so handler idempotency is mandatory.


  
Kafka's "exactly-once", precisely

  
Two distinct mechanisms, frequently conflated:

  

    
MechanismConfigWhat it actually guarantees

    
      
Idempotent producerenable.idempotence=trueBroker assigns a producer ID and tracks a monotonic sequence number per (PID, partition). Duplicate sequences from producer retries are dropped. Scope: one producer session, per partition.

      
Transactionstransactional.idAtomic writes across partitions, plus sendOffsetsToTransaction so consume-process-produce commits as one unit. The transactional.id survives restarts and fences zombies via an epoch bump. Readers need isolation.level=read_committed.

    
  

  

    The boundary
    
Kafka EOS covers Kafka to Kafka. The moment your consumer makes an HTTP call, writes to a non-participating database, or sends an email, that effect is outside the transaction and will be repeated on replay. Consumer-side idempotency is still your job.

  


  
Making consumers idempotent

  
    
    
  • Inbox table. INSERT INTO processed(message_id) ON CONFLICT DO NOTHING in the same transaction as the effect. Zero rows inserted means already handled — skip. Same pattern as the HTTP key, different identifier source.
    • 
    
  • Natural idempotency. An upsert keyed on a business ID needs no dedup table at all. Preferred where the data model allows it.
    • 
    
  • Transactional outbox. Write your state change and the outgoing message to the same database transaction; a relay publishes from the outbox. Removes the dual-write problem at its root.
    • 
    
  • Monotonic guards. UPDATE … WHERE version < :incoming makes out-of-order and repeated deliveries both harmless.
    •

What other platforms call it

  
    
    
  • AWS — ClientToken (EC2, RDS) and SQS FIFO's MessageDeduplicationId, with a fixed 5-minute dedup window.
    • 
    
  • gRPC — no header convention; put the key in metadata and check the method's idempotency level before enabling automatic retries in your service config.
    • 
    
  • Stripe — Idempotency-Key, 24-hour retention, 409 while in flight, results not saved for requests that never got a response.
    • 
  







  
Ways this breaks in production

  
    
    
  • The client regenerates the key on retry. Server-side is flawless; duplicates still appear. Generate once, persist, reuse across the whole retry loop.
    • 
    
  • Keys aren't scoped by tenant. A guessable key from another account replays their response body to you. A data breach wearing a correctness bug's clothing.
    • 
    
  • Transient 5xx cached as completed. The operation is now permanently broken and no amount of retrying will fix it.
    • 
    
  • Volatile fields in the fingerprint. Trace IDs and client clocks make every legitimate retry fail with 422. Hash the semantic payload only.
    • 
    
  • Path and method excluded from the fingerprint. The same key used against two endpoints collides and one replays the other's response.
    • 
    
  • Effect and receipt in separate transactions. Reintroduces the original ambiguity. See the crash table under Races.
    • 
    
  • No lease. One OOM kill wedges that operation permanently behind 409.
    • 
    
  • No TTL. The table grows without bound, the index stops fitting in memory, and claim latency degrades until it becomes the outage.
    • 
    
  • Invisible retries in the infrastructure. Envoy, nginx, ALBs and SDKs retry on connection errors by default. You are already receiving duplicates whether or not you designed for them.
    • 
    
  • Assuming idempotency solves concurrency. It doesn't. Different keys, different clients, lost update. Use If-Match.
    • 
    
  • Non-idempotent handlers behind idempotent methods. A PUT that appends to a log violates the contract intermediaries are relying on.
    •

How to actually test it

  
    
    
  • Fire N identical requests concurrently; assert exactly one effect and N successful responses.
    • 
    
  • Kill the process between the effect and the commit — a fault injection point in the transaction — and assert the retry produces one effect, not two.
    • 
    
  • Replay the same key with a mutated body; assert 422.
    • 
    
  • Expire the key, replay; assert a new operation is created and that this matches what you documented.
    • 
    
  • Chaos-test the store: fail over Redis or the database mid-flight and count the effects.
    •
